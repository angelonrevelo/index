# P6 — the engine against two production corpora

**Tier:** T1 (runnable + deterministic) · **Bin:** `cargo run -p index-bench --release --bin real-corpus`
**Status: PASSING, 2026-09-05.** This is the first benchmark in the repo that runs against **real
application data** rather than generated stand-ins, and it is the one that decides whether
`index-text` is worth adopting.

## Why this exists

Every other benchmark here measures synthetic data. `bench/README.md` says a benchmark that has
never gone red hasn't been shown to catch anything; this one went red **three times on defects that
no unit test on a small corpus could find**, and two of the three were real engine bugs. That is the
argument for it.

## The corpora — both exported from production databases

| | profstopick | presyo |
|---|---|---|
| file | `profstopick/research-pack/ateneo-professor-course.json` | `presyo/tests/fixtures/recall-gold-cases.json` |
| provenance | *"Ateneo registrar snapshot… sisia `class_section_all`"* | *"exported from prod 2026-06-13, ORDER BY product_id LIMIT 500"* |
| scale | **1,322 professors**, 5,143 professor×course pairings | **500 gold clusters, 2,440 real retailer listings** (1,940 indexed, 500 held out as queries) |
| ground truth | the professor the query names | `gold_product_id` — two listings match iff they share one |

Corpora are read from the sibling checkouts. Set `INDEX_CORPUS_DIR` to relocate. **A missing corpus
is skipped and announced; the bench never invents data, and refuses a verdict if neither is found.**

## The tasks

**profstopick — can a student find a professor whose name they mistyped?** Its production
measurement on 2026-08-17: **109 of 267 real searches returned nothing**, 60 of them name-shaped and
every one cross-checked to a professor already in the corpus. Its shipped matcher is 8 tiers of
prefix and substring logic with **no edit distance**, so a transposed letter finds nothing. That
matcher is **reproduced in this bench as the baseline**, so the comparison is against the real thing
rather than a straw man.

**presyo — cross-store product identity.** Given *one store's* raw listing name, find the *same
physical product* in a *different store's* catalogue. The query listing is deliberately **not
indexed**, so a hit can only come from another retailer's text. This is the hardest real task in the
house: naming disagrees on word order, abbreviation, spacing (`850g` vs `850 g`) and case.

Typo sets are generated by corrupting one alphabetic character per query with a seeded
`splitmix64` — deletion, substitution or transposition, **never at position 0** and **never on a
digit**, because corrupting a size would make the benchmark measure the opposite of what the engine
promises.

## Thresholds, and where each comes from

| Bar | Derived from |
|---|---|
| profstopick exact hit@1 ≥ **95 %** | If a clean query is worse than the prefix matcher, the engine is a regression |
| profstopick typo hit@10 ≥ **90 %** | The row this project exists for. The measured baseline is 40.8 % zero-result in production |
| profstopick must **beat the baseline** on typo hit@10 | A replacement that does not beat what it replaces is not a replacement |
| presyo cross-store recall@10 ≥ **85 %** | presyo's own Fellegi–Sunter blocker reaches 95.7 % pair-completeness using brand keys, fingerprints and trigram bands purpose-built for this job. 85 % is the bar at which a general text engine is useful as a **candidate generator** feeding it |
| **zero** size violations | Whenever the corpus contains a listing of the size the query asked for, the engine must return that size first. Any exception is a price-comparison bug |
| query p99 ≤ **5 ms** | profstopick's whole post-fix match pass measures 0.43 ms; one keystroke frame is 16.7 ms |

## Measured — 2026-09-05

Windows 11, x86-64 GNU toolchain, `rdtsc` clock, release build.

### profstopick — 1,322 professors, 4,564 terms, 29,881 B dictionary (6.55 B/term), 5 ms build

| | **engine** | baseline (the shipped matcher) |
|---|---|---|
| exact hit@1 | **99.8 %** | 99.8 % |
| exact hit@10 | **100.0 %** | 99.9 % |
| **typo hit@1** | **99.7 %** | 14.9 % |
| **typo hit@10** | **99.9 %** | 14.9 % |
| typo MRR@10 | **0.998** | 0.149 |
| **zero-result rate** | **0.1 %** | 85.1 % |

Latency on the typo set (the expensive path): **p50 42.6 µs · p99 202 µs.**

### presyo — 1,940 cross-store listings, 909 terms, 6,780 B dictionary (7.46 B/term), 2 ms build

| | recall@10 | hit@1 | MRR@10 |
|---|---|---|---|
| clean | **100.0 %** | 99.8 % | 0.999 |
| typo | **100.0 %** | 99.0 % | 0.993 |

**Size guard: 478 of 500 queries stated a mass or volume; all 478 had that size present in the
corpus; 0 violations.** Latency: **p50 33.3 µs · p99 86.5 µs.**

`INDEX_DIAG=1` additionally scores the typo set exhaustively and asserts pruned ≡ exhaustive —
**100.0 % vs 100.0 %**, which is the only thing that makes MaxScore's speed worth anything.

## The three reds it caught

**1. Unmatched query terms were scored as if they matched perfectly** — a real engine bug.
`typo_bucket` mapped a group the document matched *not at all* to `0`, identical to a perfect match.
So documents that silently **ignored** a query word outranked documents that **found it with one
typo**. Cost: **typo recall@10 of 28.8 % where it should have been 100 %**, and profstopick typo
hit@10 of 46.4 % instead of 99.9 %. Exhaustive scoring measured 28.6 % — proving it was ranking, not
pruning, and saving a fruitless hunt through MaxScore. Fixed by `MISSING_TERM_PENALTY = 3`, strictly
above the maximum edit distance. **No unit test on a small corpus can find this, because on a small
corpus every document matches every token.**

**2. A stated size lost to word overlap** — a real engine bug, and a price-comparison one.
`Purefoods Honeycured Bacon Roll Pack 500g` returned the **250 g** listing, because the 500 g
listing happened to omit two adjectives and three word-misses outweighed one size-miss. Fixed by
`MISSING_QUANTITY_PENALTY = 16`: a stated size is not just another word. Safe when the corpus
carries no listing of the requested size — every candidate is penalized identically, so the relative
order is unchanged and the engine still answers.

**3. The guard itself reported three violations that were not violations** — a benchmark bug.
`MILKMAN YOGURT DRINK STRAWBERRY 6S 100ML` has `6S` as its first quantity token, which parses as
6 *pieces*; comparing that against the query's `100 ml` produced spurious failures. A pack count is
not a size. Fixed by comparing mass/volume only. **A benchmark that reports the wrong defect is
worse than no benchmark**, so this is recorded rather than quietly patched.

## Promotion

This benchmark **passes today** and is eligible to move out of `bench/roadmap/` into the live gate
as soon as the two corpora are vendored into this repo (or a fixture subset is), so that it does not
depend on sibling checkouts being present. Until then it stays gate-excluded — a gate that silently
skips is not a gate.

## Reproduce

```sh
cargo run -p index-bench --release --bin real-corpus
INDEX_DIAG=1 cargo run -p index-bench --release --bin real-corpus   # + pruned vs exhaustive check
INDEX_CORPUS_DIR=/path/to/checkouts cargo run -p index-bench --release --bin real-corpus
```
