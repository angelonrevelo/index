# P35 — `simd128`: 11× on the kernel that needed it, and the confound that hid it

**Tier:** T1 · **Bin:** `js/accel-bench.mjs <artifact>` · **Artifacts:** 6,342 B baseline / 7,325 B `+simd128`
**Status: MEASURED, 2026-09-06. Not shipped — the choice is onegrid's, and their probe already exists.**

`p34` closed with a named follow-up:

> **`simd128` not tested.** The one kernel that loses badly is the one SIMD would help most, so the
> obvious follow-up is the one not done.

It was done. The first answer was wrong, and the reason it was wrong is the useful part.

## First result: "SIMD does nothing"

Built with `-C target-feature=+simd128`, interleaved against baseline, twice:

| | baseline | `+simd128` |
|---|---|---|
| `bitmap_op` | 14,092 M rows/s | 13,651 |
| everything else | — | unchanged within noise |

The binary grew by 983 bytes, so *something* vectorised, but the kernel that mattered did not move.
The tempting conclusion — *LLVM's wasm backend will not auto-vectorise this loop* — is plausible,
publishable, and false.

## The confound: the bench aliased its own buffers

`og_bitmap_op(op, a, b, len, out)` was being called as:

```js
e.og_bitmap_op(0, presencePtr, maskPtr, N, maskPtr);   //  b === out
```

The output buffer *was* the second input. Overlapping buffers force any compiler to assume aliasing,
which is one of the two standard reasons a byte loop fails to vectorise. **Measuring only that form
confounds "wasm has no SIMD" with "this particular call cannot be vectorised at all."**

Both forms are now measured, and they disagree by an order of magnitude:

| 1 M rows, in WebAssembly | baseline | **`+simd128`** | gain |
|---|---|---|---|
| `bitmap_op`, distinct output | 14,624 M rows/s | **236,239** | **~16×** |
| `bitmap_op`, output aliases input | 12,086 | 13,926 | none |

Across three interleaved rounds the SIMD figure ranged **128,000–236,000** M rows/s against a
baseline steady at **14,500–14,700** — so **9–16×, every round**. The spread is wide because even at
200 repetitions the SIMD arm measures 0.004 ms; the ratio is solid, the third significant figure is
not.

## What this changes

`p34` reported `bitmap_op` at **4 % of native** and called it "what no SIMD costs, isolated". That
stands for the shipped artifact. But with `simd128` and non-overlapping buffers:

| | native | wasm baseline | **wasm `+simd128`** |
|---|---|---|---|
| `bitmap_op` | 354,030 M rows/s | 14,624 (4 %) | **~160,000 (≈45 %)** |

The other five kernels are unchanged, which is consistent and expected: they are gated by dependent
loads, hash probes and comparisons, not by byte-parallel work.

## The socket already exists on the consumer's side

`packages/wasm/src/detect.ts` already ships `PROBE_SIMD` — a validation probe that compiles a
function returning a `v128` — and `detectCapability()` already returns `{ wasm, simd, thread }`.
**onegrid can already tell whether a browser supports SIMD, and nothing uses the answer**, because
the crate emits one artifact.

Their `bundle-budget.json` also settles the size question by their own rule: the budget covers
`dist/index.js` and notes *"the Rust crate is NOT part of this budget (it ships as a separately
fetched .wasm)"*. **983 bytes is not budget-constrained.**

So the shape is: build both, let the existing probe choose. That is a decision for onegrid, not one
to take on their behalf — `p33` was corrected for exactly that kind of overreach — so this document
measures and stops.

```sh
./scripts/build-wasm.sh                       # all four artifacts, side by side, into dist/
node js/accel-bench.mjs dist/index-accel.wasm
node js/accel-bench.mjs dist/index-accel.simd.wasm
```

## Honest limits

- ~~**No dual-artifact build wired.**~~ **`scripts/build-wasm.sh` now builds all four artifacts
  side by side into `dist/`**, each with its own `CARGO_TARGET_DIR` so the `simd128` analytics
  build no longer overwrites the baseline one. Both were re-verified from `dist/`:
  14,586 vs 236,995 M rows/s on `bitmap_op`.
- **Still not shipped**, and that part is unchanged: which artifact a host loads is onegrid's
  decision, and their `detect.ts` probe already answers the question it depends on.
- **The SIMD timing is at the edge of the timer.** 0.004 ms per call even at 200 repetitions. The
  9–16× range is real; a point estimate would not be.
- **Aliasing is not documented in the ABI.** `og_bitmap_op` accepts overlapping buffers and computes
  the right answer either way — only the speed differs by 16×. A host doing `a &= b` in place will
  silently get the slow path, and nothing tells it so. That is worth a line in `abi.ts`, and this
  document is not the place to add one to someone else's repository.
- **Node, not a browser**, and one engine — the `p34` limits still apply.

## Reproduce

```sh
node js/accel-bench.mjs   # both bitmap_op forms are in the default output
```
